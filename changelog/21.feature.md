Added `ZenodoClient.upload_file`, which uploads a file to a record's draft
using InvenioRDM's three-step initialise, upload, commit flow.
It returns a `FileEntry`, which reports the file's name, size, checksum
and status, and keeps everything else Zenodo said about it in `raw`.

It is built to survive a flaky network and a slow one:

- a failed upload is tried again,
  re-reading the file and resetting the progress bar each time.
  The retries on the session cannot help here,
  because the request streams a file handle which cannot be replayed.
- by default we check that Zenodo received the bytes we sent,
  by comparing the file's local MD5 checksum
  against the checksum Zenodo reports.
  A corrupted transfer raises the new
  `openscm_zenodo.exceptions.ChecksumMismatchError`,
  and is tried again before it does.
- uploading a name which is already on the draft replaces it,
  including when it was left behind by an upload which died part way through.
  A draft with a half-uploaded file on it cannot be published,
  so we also clean up after ourselves when an upload fails for good.
- there is one progress bar per file, which disappears when the file finishes.
  Bars silence themselves when standard error is not a terminal,
  so continuous integration logs stay clean,
  and `progress=False` turns them off explicitly.

Also added `ZenodoClient.delete_file`, `openscm_zenodo.checksums`
and `openscm_zenodo.progress`.
MD5 hashing is CPU-bound and easy to mistake for slow I/O,
so `openscm_zenodo.checksums.get_file_md5` logs how long it took,
at `INFO` when a single hash takes more than a few seconds.
