Added support for creating new versions of a record:

- `ZenodoClient.new_version`, which creates the next version of a published
  record. It is get-or-create: a record can have at most one unpublished next
  version, so calling it again returns the draft that already exists.
  Unlike the legacy API, any published version can be the starting point,
  not just the latest one.
- `ZenodoClient.inherit_files`, which carries the previous version's files over
  and hands back the draft's files afterwards. Zenodo copies them across itself,
  so nothing is uploaded and no storage is duplicated. A draft which already has
  files is left exactly as it is, because Zenodo only imports into an empty one,
  so a release script which failed part way through can simply be re-run.
- `ZenodoClient.publish`, `ZenodoClient.update_metadata`
  and `ZenodoClient.get_latest_version_id`.
- `create_new_version`, which does the whole thing in one call:
  create the version, set its metadata, get its files into the state you want
  and optionally publish it.

How the new version treats files is chosen with `FilesMode`:
`start_fresh` (the default) begins from an empty draft,
`inherit` carries the previous version's files over and adds to them,
and `mirror` carries them over and then makes the file list match exactly,
deleting anything else. `mirror` refuses to run without an explicit list of
files, since it deletes whatever is not in that list.

The whole path is safe to re-run: a run which failed part way through
resumes the same draft, imports are skipped when the draft already has files,
and unchanged files are not uploaded again.
