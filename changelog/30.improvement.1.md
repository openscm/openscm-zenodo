Made writing files to a published record fail immediately, and say why.

Zenodo locks a published record's files, so it refuses these writes itself — but
it refuses them one request at a time, with a bare `404` or `403`, and only once
the work has started. `upload_files`, `mirror_files`, `delete_files` and the rest
now check the record first and raise `RecordNotWritableError`, which names
`create_or_get_new_version` as the way to release a change:

```
Record '584092' on https://zenodo.org is published, so its files cannot be
changed. Zenodo locks them when a record is published. To release a change,
create a new version with `openscm_zenodo.zenodo.ZenodoClient.create_or_get_new_version`.
```

The check costs one request per call, not per file. The same error is raised if
somebody publishes the record while the write is in flight, so the race reads no
differently from the ordinary case. `inherit_files` now reports a published
record as the error it is, rather than quietly doing nothing the way it does for
a draft which already has files.

Two reads which the same race could break now recover instead of failing:
`is_draft` looks once more for a published record before saying it cannot find one
at all, and `list_files` falls back to the published listing when a draft's
listing disappears underneath it.
