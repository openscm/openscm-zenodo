Rewrote metadata around Zenodo's InvenioRDM schema, and gave records a type.

`openscm_zenodo.metadata` is the schema as classes: `Metadata`, and the
`Person`, `Organisation`, `Creator`, `Contributor`, `Affiliation`, `Identifier`,
`Right`, `Subject`, `Date`, `RelatedIdentifier`, `Funder`, `Award` and `Funding`
it is built from. `ZenodoClient.get_metadata` returns a `Metadata`,
`ZenodoClient.update_metadata` takes one, and `get_published`, `get_draft` and
`get_record` return a `Record` carrying the metadata, `access` (an `Access`),
`pids`, `parent_id` and `versions` (a `Versions`), with `doi` and `parent_doi`
alongside them. As with `FileEntry`, what we model is parsed and everything else
Zenodo sent is kept in `raw`, so a response shaped differently to what we expect
fails where we read it.

People and organisations are separate classes, as are creators and
contributors, because Zenodo's rules for them differ: a person needs a
`family_name`, an organisation needs a `name`, and a contributor needs a `role`
which a creator may not have. Those are now guaranteed by construction rather
than checked at the end.

Metadata read off one record can be applied to another as it is. The display
text Zenodo adds to vocabulary entries (a resource type's title in every locale,
a licence's description and icon) is dropped on the way back, because it is
Zenodo's to fill in. This is why there is no `user_controlled_only` flag:
`Metadata` only ever serialises the shape Zenodo accepts, so there is nothing
left to strip.

Metadata written for the legacy deposit API now fails before it is sent, naming
the key which gave it away and what to write instead — `upload_type` →
`resource_type`, `license` → `rights`, `keywords` → `subjects`, `access_right` →
the record's `access`, and so on.

**Zenodo discards values it cannot read rather than refusing them**, which is
the reason to validate at all: a malformed `publication_date` or an over-long
`version` comes back as a `200` with the field simply missing. So
`Metadata.find_problems` and `Metadata.validate` check the metadata is complete
and report every problem at once, `publish` runs that check before the step
which cannot be undone, and `update_metadata` compares what came back with what
it sent and warns about anything Zenodo dropped. `publication_date` is checked
against EDTF level 0, which is what Zenodo actually takes, so `"2021"`,
`"2021-03"` and `"2021-03-09/2021-04-10"` are all accepted.

A published record's metadata can be corrected in place — same ID, same DOI —
and that is now reachable, but only deliberately.
`ZenodoClient.create_or_get_edited_metadata_draft` starts the edits, and
`update_metadata` refuses a published record which has not had them started,
raising `RecordNotWritableError` rather than surfacing Zenodo's bare `404`.
`ZenodoClient.has_edited_metadata_draft` answers "are there edits waiting to go
out?", which is a different question from `is_draft`'s "has this record ever
been published?" — so `is_draft` loses its `files_based` argument and the
`NotImplementedError` it existed to raise. These methods apply only to published
records and raise `DraftRecordDraftMetadataEditsError` otherwise, because a
record which was never published *is* a draft. `Record.is_draft` and
`is_published` were likewise two names for one question, so `is_published` is
gone and `is_draft` is its opposite; `Record.is_edited_metadata_draft` marks the
document which holds a published record's pending edits.

Zenodo serves an unpublished record and a published record's pending metadata
edits from the same endpoint, and they are not the same thing, so two methods
read them. `ZenodoClient.get_draft` returns an unpublished record and **never**
returns pending edits, raising `PublishedRecordDraftError` for a published
record whatever state it is in. `ZenodoClient.get_edited_metadata_draft` reads
the edits, and only reads — starting them stays the deliberate act that
`create_or_get_edited_metadata_draft` is — raising
`DraftMetadataEditsNotFoundError` when there are none.

Renames, in the same spirit of saying what things do:
`ZenodoClient.new_version` and the `create_new_version` helper are
`create_or_get_new_version`, because they return the version already in progress
rather than always creating one, and `create_or_get_*` is the word order used
for this pattern throughout; `get_draft` now raises `DraftNotFoundError` naming
the way forward instead of a bare HTTP error.

Every method which takes a record ID also takes a `Record`, so a record which
has just been handed back can be passed straight on.

Zenodo's metadata schema, and the map from the legacy one, are documented under
"Further background".

Warnings about things Zenodo has quietly ignored now go through
`warnings.warn`, with a `ZenodoWarning` category, rather than through our
logger. The logger is disabled until a caller turns it on, so these previously
never appeared for anyone who had not configured logging — which is precisely
the person who needs to hear that a field they set was discarded. They can be
silenced or promoted to errors as a group with
`warnings.simplefilter("error", ZenodoWarning)`.

`Metadata.find_unknown_vocabulary_values` replaces `has_known_resource_type`
and covers every vocabulary field we model: resource types, identifier schemes
(`KNOWN_IDENTIFIER_SCHEMES`) and relation types (`KNOWN_RELATION_TYPES`). Each
report names where the value is (`related_identifiers[0].relation_type`, which
matters on a record with several creators), the closest value we do know of, and
then that vocabulary in full — so a typo can be fixed from the message rather
than by going looking. Matching is done against the lower-cased value, because
the mistake it catches most reliably is the DataCite spelling of a relation type
(`isSupplementTo` rather than `issupplementto`), and that would otherwise get no
suggestion at all. `update_metadata`'s flag for this is now
`warn_unknown_vocabulary`.

`Person.TYPE` and `Organisation.TYPE` carry the `type` values Zenodo uses,
rather than module-level constants sitting away from the classes they describe.

Separately, uploads now notice a failure Zenodo reports as a success.
It answers a failed file transfer with a `200` whose body carries an `errors`
key, a `size` of zero and no checksum, and the file then disappears from the
draft, so the upload used to die two steps later on `Record 'X' has no file 'Y'`
— which points at the wrong thing entirely. The content response is now checked
for that, raising `FileTransferFailedError`, which is in the retry set because
these failures are usually transient.
