Added the write paths for making a record and for the parts of it which are
neither files nor metadata.

`ZenodoClient.create_record` is the only way to make a record from nothing.
Everything else which creates one derives it from a record that is already
there, so without this the library could only extend chains something else had
started. It returns a `Record`, which every method taking a record ID also
accepts, so a new record can be passed straight on to `upload_files` and
friends. Zenodo mints two IDs here, the record's own and its parent's, and the
record is unpublished until `publish` is called — which is all "draft" means.
There is no second object.

**It takes no arguments.** A new record is unpublished, and an unpublished
record is invisible to everyone else: an unauthenticated request gets a `404` on
the published endpoints and a `403` on the draft endpoints and the file content,
whether the record's files are "public" or "restricted". So there is no window
in which anything is exposed and nothing has to be set at creation, which leaves
one home for each thing — `update_metadata` for metadata, `update_access` for
access, `upload_files` for files — and all of it only has to be right before
`publish`.

`ZenodoClient.update_access` changes who may see an unpublished record and its
files. `Access` and `Embargo` gained `to_json`; `Access.status` is Zenodo's
summary of the other fields and is never sent.

**`update_access` reads the record before it writes it, and it has to.**
Zenodo's `PUT` is a *replace* for `metadata` and a *preserve* for `access`,
which is not symmetric: sending only an access block leaves the record with no
metadata at all — no title, no creators, nothing. So the metadata Zenodo
currently holds is sent straight back alongside the new access, in Zenodo's own
serialisation rather than through a round trip of ours, because the point of the
call is that the metadata does not change.

`ZenodoClient.reserve_or_get_doi` gets a record's DOI, reserving one if it does
not have one yet, so that a record's own DOI can be written into the files or
metadata it is published with. It asks the record first, so anything which
already has a DOI — reserved earlier, or minted by publishing — simply hands it
back. That is what makes it safe to call repeatedly, which Zenodo is not: a
second reservation is a `400 A PID already exists for type doi`.

Two things Zenodo refuses which are now translated rather than surfaced raw:
`AccessNotPermittedError` says that only an admin can restrict a *record* and
points at `Access.files` and `Embargo` for what does work, and
`RecordNotWritableError` covers a draft which is not there to write to.

Two things Zenodo will not let an ordinary account set, both found against the
sandbox and both now covered by tests so we notice if they change:

- `access.record="restricted"` is refused outright, including on a record the
  token created moments earlier, so it is about the field rather than ownership.
  Restricted *records* are therefore not reachable through the API; restricted
  *files*, with or without an embargo, are. We still send it rather than blocking
  it ourselves, since the rule is Zenodo's and may change.
- `files.enabled=false`, i.e. a metadata-only record, is refused *quietly*: the
  request succeeds, files stay enabled, and the refusal appears only in an
  `errors` array in the response body.

So `update_access` warns about settings Zenodo declined to apply without refusing
the request. Only fields which were actually sent are reported, via the new
`was_field_sent`: the same `errors` array also carries "this draft is not
finished yet", which is the normal state of a draft — Zenodo only insists on
complete metadata at publish time — and warning about that would bury the case
which matters.

Warnings now point at the line which led to them rather than at a line of ours,
whatever depth of our own helpers they are raised beneath. Counting stack frames
by hand cannot be right in general — the count changes whenever a helper is added
— and correcting it would have meant a `stacklevel` parameter on every public
method, so `warn_zenodo` walks the stack to the first frame outside the package
instead. This is the same approach as pandas' `find_stack_level`; Python 3.12's
`warnings.warn(skip_file_prefixes=...)` does it natively and should replace it
when the supported floor gets there.

The pre-InvenioRDM `get_reserved_doi` is now `get_reserved_doi_legacy`, so the
name is free. A record's DOI, reserved or minted, is `Record.doi`. It goes when
the command-line interface is trimmed.

**Putting a record in a community is not supported, and will not be.** On the
legacy API `communities` was a metadata field; on InvenioRDM it is not a field at
all. Submitting a record to a community creates a review request which a curator
of that community accepts or declines, and a community-bound draft is published
by that acceptance rather than by `publish`. That is an asynchronous flow with a
state machine owned by somebody else, which is a different thing from everything
else here. Use Zenodo's web interface. Metadata carrying a legacy `communities`
key is refused with a message saying so, rather than having it silently dropped,
and the communities a record is already in can be read from
`Record.raw["parent"]["communities"]`.

Separately, the tests which write to Zenodo now ask `resolve_token` whether a
sandbox token is available rather than looking for `ZENODO_TOKEN` themselves.
A token in `ZENODO_SANDBOX_TOKEN` — which is where a sandbox token belongs, and
what `.env.example` now shows — used to skip the entire suite in silence.
