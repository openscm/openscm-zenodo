**The legacy deposit API is gone, and the command-line interface is now three
commands.** Zenodo replaced the deposit API with InvenioRDM, and this release is
written against InvenioRDM only. There is no compatibility layer. See
["Migrating from v0.x"](migration.md), which is the shortest path from working
v0.x code to working code today.

`ZenodoInteractor` and the `*_legacy` functions (`retrieve_metadata_legacy`,
`retrieve_bibtex_entry`, `create_new_version_legacy`, `get_reserved_doi_legacy`)
are deleted. Use [`ZenodoClient`][openscm_zenodo.zenodo.ZenodoClient]; the
migration guide maps every method across.

The CLI keeps the tasks which are genuinely better from a shell — moving bytes in
and out, and getting a citation:

```sh
openscm-zenodo upload-files   RECORD_ID data/a.nc data/b.nc
openscm-zenodo download-files RECORD_ID a.nc b.nc --dest-dir data/
openscm-zenodo retrieve-citation RECORD_ID
```

`retrieve-metadata`, `update-metadata`, `remove-files` and `create-new-version`
are removed. They took structured JSON input, which belongs in Python where the
new metadata schema can be built and validated; the migration guide gives the
one-line Python equivalent for each. `retrieve-bibtex` is renamed and generalised
to `retrieve-citation`, whose `--format` defaults to `bibtex`, so the old
behaviour is what you get by not passing anything.

`download-files` is new: it takes remote filenames the way `upload-files` takes
local paths, and naming none of them downloads all of them. Drafts, restricted
and embargoed records need no flag — a record ID already says whether it is a
draft, and access is just the token.

On `upload-files`, `--delete-extraneous` is now `--mirror`, the one flag which
deletes anything, and `--sync` is gone because it has nothing left to switch on:
files already on the draft with the same contents are never re-uploaded. `--zip`
bundles everything into one archive, which is how a directory structure survives
Zenodo having no directories.

`--token` no longer declares `ZENODO_TOKEN` to typer. The whole chain — `--token`,
then `ZENODO_SANDBOX_TOKEN` on the sandbox, then `ZENODO_TOKEN`, then a `.env`
file — now lives in one place, so the CLI and the Python API agree about where a
token comes from. **If you talk to the sandbox, put its token in
`ZENODO_SANDBOX_TOKEN`.**
