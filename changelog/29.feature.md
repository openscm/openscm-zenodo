Made it visible when Zenodo flattens a local path, and added a way to avoid it.

Zenodo has no directories: a file is identified by its name alone, so
`out/2024/data.nc` is uploaded as `data.nc` and everything above it is lost.
That has always been true and was never said out loud.

`upload_file`, `upload_files` and `mirror_files` now warn when a path is about to
be stripped, naming each file and what it will land as. Pass
`warn_path_stripped=False` to silence it. The warning is an `OpenSCMZenodoWarning`, so it
appears whether or not logging is configured, and it is raised once per call
rather than once per file — partly so it is not repeated, partly because a
warning raised inside an upload worker thread would be attributed to our stack
rather than to the line which asked for the upload.

**Several files which share a name are now a `DuplicateFileKeyError` rather than
a silent loss.** `upload_files(record, ["2024/data.nc", "2025/data.nc"])`
previously uploaded whichever finished last and said nothing. There is no right
answer to guess at, so it is refused, before any request is sent, with a message
naming both paths and the three ways out: rename them, upload them separately, or
zip them. The same file named twice is not a collision — that is one upload.

The new `openscm_zenodo.zipping` module is the way to keep a structure:

```python
from openscm_zenodo import zip_files

zip_files([Path("out/2024/data.nc"), Path("out/2025/data.nc")], Path("results.zip"))
# stores 2024/data.nc and 2025/data.nc
```

`ZenodoClient.upload_files_as_zip` does that and uploads the result in one call.
Paths inside the archive are relative to `base_dir`, which defaults to the
deepest directory containing all of them, so the obvious call does the obvious
thing. Zenodo's web interface shows what is inside an archive, so the contents
stay browsable.

**The archives are deterministic**, and that is load-bearing rather than tidiness.
A stock archive records each file's modification time, so re-zipping the same
files produces a different checksum every time — and uploads skip only those
files whose name and checksum already match, so every re-run would have uploaded
the whole archive again. Members are sorted and their metadata is pinned, which
makes zip-then-upload idempotent. Pass a `DeterministicZipValues` to choose what
they are pinned to — a timestamp, permissions and host system, to match an
existing archive byte-for-byte or to mark something executable — or
`deterministic=False` if the real mtimes matter more.
